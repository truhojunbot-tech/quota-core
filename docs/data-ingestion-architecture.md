# Data Ingestion Architecture

## Purpose

This document explains where usage and quota data come from, how they are normalized, and which layer owns each step.

The public package owns the normalized schema, adapters, local scanners, aggregation helpers, and dashboard renderer. Private operations may provide live provider monitors, private aliases, history databases, and generated artifacts, but those private components must feed public `quota_core` through normalized snapshot APIs.

## End-To-End Flow

```text
raw provider files / live monitors / private history DBs
        -> provider-specific collector or scanner
        -> public provider adapter
        -> NormalizedSnapshot
        -> dashboard HTML / reports / alerts
```

Rules:
- Raw provider data is parsed before dashboard rendering.
- Dashboard code consumes `NormalizedSnapshot` only.
- Provider-common aggregation belongs in `quota_core.adapters.projects`.
- Display semantics belong in dashboard formatter/helper APIs and are documented in [reporting-semantics.md](reporting-semantics.md).

## Public Local Scan Path

The public `quota-core scan` command reads configured local paths and emits normalized snapshots.

| Provider | Public local input | Public scanner output | Notes |
| --- | --- | --- | --- |
| Claude | Configured Claude transcript roots, such as `~/.claude/projects` | `local_all` window | Local observed history, not provider quota telemetry |
| Codex | Configured Codex state database, such as `~/.codex/state_5.sqlite` | `local_all` window | Local observed history from Codex threads |
| Gemini | Configured Gemini tmp/session directory, such as `~/.gemini/tmp` | `local_all` window | Local observed history from session JSON/JSONL files |

Public local scanners do not infer live quota reset windows unless the provider adapter receives live quota payloads. Missing paths should produce warnings, not crashes.

## Provider Adapter Responsibilities

Provider adapters normalize raw collector payloads into the public snapshot schema.

Adapter responsibilities:
- Convert provider-specific window names into public window names.
- Compute `window_start`, `window_end`, and `resets_at` when known.
- Choose authoritative provider totals according to provider semantics.
- Normalize project names and model names through shared helpers.
- Populate `runtime` as a nested runtime-only slice when present.
- Preserve freshness via `cache_state` and `stale`.

Provider adapters must not push provider-specific repair logic into dashboard components.

## Private Quota Overlay Flow

The private Quota deployment can enrich public local scans with live quota telemetry and historical usage timelines.

The private snapshot generator follows this sequence:

1. Load public config through `quota_core.config`.
2. Run public `scan_config(config)` for baseline local snapshots.
3. Fetch provider-specific live quota payloads through private monitors.
4. Normalize each live payload with public adapters:
   - Claude: `normalize_claude_quota()`
   - Codex: `normalize_codex_quota()`
   - Gemini: `normalize_gemini_usage()`
5. Attach private history payloads under `snapshot.history`.
6. Serialize snapshots with `snapshot_to_dict()`.
7. Render dashboard HTML with the public dashboard CLI.

Private overlay code owns polling and storage details. Public core owns the normalized schema and display behavior.

## Private Usage Sources

The private Quota deployment currently uses these usage source classes.

### Claude

Quota windows:
- collected by a private Claude quota monitor
- normalized by `normalize_claude_quota()`
- can fall back to a cached or manually supplied usage override when live quota collection fails

Usage timeline:
- read from a private project usage database
- converted to a 30-day cost timeline
- private project aliases may be applied before attaching the timeline

Quota history:
- read from private Claude quota history storage when live quota history is available

Session analytics:
- generated by public `quota_core.session.analyze_claude_sessions()` from configured Claude transcript roots
- private aliases may be applied through a normalizer callback
- cached by private ops to avoid expensive rescans
- reconciled against the provider quota scanner total when available

### Codex

Quota windows:
- collected by a private Codex monitor
- normalized by `normalize_codex_quota()`
- the adapter prefers raw `total_tokens` over `tokens_used` when present
- runtime-only projects from `runtime_by_project` are included in the main project breakdown through shared project aggregation helpers

Usage timeline:
- read from private Codex history tables, including daily usage and runtime exec logs
- converted to a 30-day token timeline
- this history is not the same denominator as the current Codex quota window

Quota history:
- read from private Codex monitor history when available

### Gemini

Quota windows:
- collected by a private Gemini monitor
- normalized by `normalize_gemini_usage()`
- can include quota groups by model family

Usage timeline:
- read from Gemini session files under the configured Gemini session directory
- converted to a date-bucketed token timeline
- private project aliases may be applied before attaching the timeline

## History Versus Quota Windows

History sources and quota windows answer different questions.

| Data | Question answered | Example display |
| --- | --- | --- |
| Quota window | How much of the provider quota window is currently used? | `7일 창`, utilization, reset/freshness |
| Runtime slice | How much of that window came from runtime-tagged work? | `75.3%` runtime share |
| Usage timeline | What happened over a historical date range? | `30일 사용량 히스토리` |
| Session analytics | Which transcript-derived sessions/prompts drove usage? | `Claude Sessions` |

Dashboard labels must make this distinction visible.

## Generated Artifacts

Generated snapshot and dashboard files are runtime artifacts. They are not the public source of truth.

The source of truth is:
- public schema and adapters in `quota_core`
- private overlay collectors in private ops
- generated snapshot JSON for one sampling moment

A dashboard change that affects private deployment output must regenerate both snapshot JSON and dashboard HTML before visual verification.

## Operational Verification

When a private deployment serves the dashboard, verify the actual configured dashboard URL and port.

Do not assume that a temporary static server, a local file, or a previous generated artifact matches what the user sees. The acceptance checklist in [reporting-semantics.md](reporting-semantics.md) applies to every dashboard-facing data ingestion change.
